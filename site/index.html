Customer report → pull request

Turn a customer's bug report into a reviewed fix, without trusting the report.

A support rep forwards what the customer wrote. An agent reproduces the bug with a failing test, fixes it inside a throwaway sandbox, and the hub opens a pull request. A developer merges it, and the hub can't.

How it works

From the support inbox to a pull request

No developer has to reproduce anything. They get a pull request with a failing test, a fix and a receipt of everything the agent saw and tried.

Forward

The support rep forwards a customer's report from the inbox. The text is treated as data: scanned for steering attempts and wrapped before any model sees it.

Reproduce

The agent may only add a new test, and it has to fail for real in the sandbox. No red test, no next step.

Fix

It changes code inside its role's scope until the reproduction passes and nothing else breaks. Every edit is checked against the policy before it's written.

Review

The hub pushes a task/<id> branch and opens a pull request. The rep gets a drafted reply for the customer. A developer merges on GitHub.

Every task ends one way, and the rep gets a reply to send

pr_openedA failing test and a fix exist. A pull request waits for a developer.
gave_upNo fix within the scope, or the agent chose to stop. The reason shows on the receipt.
flaggedThe report tried to steer the agent. Stopped before any sandbox or model call. No pull request.
errorSomething failed, including a patch refused at publish time. Nothing is published.
Architecture

One VM, one trusted hub, many throwaway sandboxes

The hub holds the secrets and a clone of the product repo. Untrusted code runs only in short-lived containers that hold no secrets. Untrusted text reaches a model, never a decision.

trusted untrusted code outside the VM

packages/agent

Role policy, input scanner, context builder, the edit format and its guardrails, the reproduce-then-fix loop and its stop rules, the reply draft.

packages/sandbox

runInSandbox: one container per command, env built from scratch, read-only root, all capabilities dropped, 1 GB / 1 CPU / 120 s.

apps/hub

Fastify: tasks, the event stream over WebSocket, the real pipeline, the fixture run, and the GitHub publisher.

packages/shared

The contract between hub and UI. Every status change is an event; the task snapshot is derived from the stream, so the audit trail is the source of truth.

Containment

Assume the report is hostile

The input scanner warns; the layers below protect. Each one shows up on the task's receipt, and a flagged report can replay a scripted hostile proposal to show every layer refusing it.

Untrusted text

Customer words go into prompts only inside <untrusted> markers, and never decide anything on the host.

Write scope

Each role may add tests widely and change code narrowly. Deny wins. Three refusals flag the task.

The .hub/ lock

Role files and prompts are never agent-writable, so a report can't talk the agent into widening its own scope.

No network

Checks and fixes run with --network none. A test that tries to phone home is blocked and halts the task.

No secrets

No env files, no npmrc, no mounts but /work and a read-only dependency cache.

Only what was edited

The diff holds only paths the agent edited through the policy check, re-checked before it's published.

The hub can't merge, not just won't

  • GitHub enforces it. A ruleset on main requires a pull request with one approving review, with an empty bypass list, so it binds admins too.
  • The token is a bot's. Fine-grained, one repo, Contents and Pull requests only. A push to main gets GH013, a merge gets 405.
  • The bot can't approve its own pull requests, so a developer always reviews.
  • A flagged report never opens a pull request, and its reply to the customer is a fixed template.
